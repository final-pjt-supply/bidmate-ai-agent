# BidMate 공고 정규화 Lambda — 배포 가이드

`normalize_output_adapter.run()`을 람다로 실행하는 배치.
증분 처리(신규·재병합·버전상이 공고만)라 평상시 소량이며 15분 안에 충분히 끝난다.

## 실배포 현황 (2026-07-27 기준)

| | |
|---|---|
| 함수명 | **`realtime-normalize-dev`** (ap-northeast-2) |
| 패키지 | **zip** — 콘솔 코드 편집기로 직접 관리 |

> **다른 이름**의 함수를 만들기 때문에, 남겨두면 `sam deploy` 시 중복 함수가 생긴다.

## ⚠️ 전건 재정규화 전 필독

**`NORMALIZER_VERSION`을 올려 전건(19k)을 재정규화할 때는 이 람다를 반드시 멈출 것.**

콘솔 → 함수 → **구성 › 동시성 및 재귀 탐지** → **동시성** 편집 →
**동시성 예약 = 0** → 저장. (복구는 "예약되지 않은 계정 동시성 사용")

안 그러면 람다가 구버전 코드로 같은 공고를 나중에 덮어써서 **작업 결과가 통째로 사라진다.**

> 실측 2026-07-27: 로컬에서 v1.8로 19,076건을 45분에 걸쳐 정규화 완료했으나,
> 그 사이 돌던 이 람다(당시 v1.7)가 전량을 덮어 `normalizer_version`이 v1.7로 되돌아갔다.
> 45분 작업이 통째로 유실. 어댑터는 **단일 실행 기준으로만 멱등**하고
> 동시 실행은 막아주지 않는다.

전건 재정규화는 **로컬/EC2/일회성 스크립트**로 돌린다. 람다는 그 뒤 증분만 담당.

## 코드 갱신 절차

`normalizer.py` / `normalize_output_adapter.py`를 고쳤을 때.

1. 콘솔 → 함수 → **코드** 탭 → 코드 편집기
2. 좌측 트리에서 두 파일을 열어 **로컬 최신본으로 전체 교체**
   (정본: `bidmate-ai-agent/normalizer/` — 무수정 복사)
3. 편집기 상단 **Deploy** 클릭 ← 누르지 않으면 반영 안 됨
4. **테스트** 탭 → 이벤트 `{}` → Test 1회
5. **모니터링 › CloudWatch 로그**에서 `대상 공고 N건` 확인
   - 재정규화 직후라면 **수십 건 이내**가 정상
   - 19,076건이 나오면 Deploy가 안 먹은 것 → 즉시 동시성 0으로 되돌릴 것

편집기가 안 뜰 만큼 패키지가 크면 **작업 › 함수 코드 다운로드** →
두 파일 교체 → 재압축 → **코드 소스 › 업로드**.
재압축은 **폴더가 아니라 내용물을 압축**해야 한다(`cd 폴더 && zip -r ../fn.zip .`).
경로가 한 겹 더 생기면 핸들러를 못 찾는다.

## 환경 변수

DB 접속은 아래 우선순위로 해석된다 (`lambda_function._resolve_dsn`).

1. `DB_DSN` — psycopg conninfo 문자열 통째로. 있으면 최우선.
2. `DB_SECRET_ARN` — Secrets Manager ARN (시크릿=DSN 또는 `{"DB_DSN":...}`). IAM 권한 필요.
3. 개별 조립 — `DB_HOST` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` / `DB_PORT`(기본 5432)

`DRY_RUN` = `"1"`이면 미기록(계획 로그만). 기본 `"0"`.
이벤트로 1회 오버라이드: `{"dry_run": true}` → env가 0이어도 그 호출만 미기록.

네트워킹: 람다는 RDS와 같은 VPC의 프라이빗 서브넷, RDS 보안그룹에 5432 인바운드 허용.

## 운영 주의

- **증분 전용.** `select_targets`가 신규·재병합·버전상이만 고른다.
- **멱등·재개가능.** 공고 단위 `DELETE(summary CASCADE) → INSERT`를 한 트랜잭션으로 처리하고
  autocommit이라, 중간 실패해도 성공분은 커밋되고 실패분은 다음 실행에서 자동 재시도.
  단 **동시 실행은 막아주지 못한다**(위 경고 참조).
- **락 짧음.** 공고 단위 트랜잭션이라 장시간 락 없음.
- **백로그 대비.** 대상이 수천 건 쌓이면 15분 초과 가능.
  호출 주기를 짧게 하거나 `select_targets`에 `LIMIT + 반복 호출` 도입(향후 과제).

## 모니터링

- CloudWatch 알람: 함수 Errors ≥ 1, Duration > 12분(타임아웃 임박).
- 로그 메트릭 필터: `실패 공고` 문자열 → 알람.
- 전건 재정규화 중 진행 점검:
  ```sql
  SELECT normalizer_version, count(*), max(normalized_at)
  FROM bid_require_summary GROUP BY 1;
  ```
  `v1.7`처럼 구버전 카운트가 **다시 늘어나면** 다른 프로세스가 덮고 있는 것이다.
